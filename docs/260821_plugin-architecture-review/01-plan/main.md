# 260821_plugin-architecture-review — 리뷰 헌장 (Review Charter)

> **이 문서의 용도**: 다른 세션에서 이 문서만 읽고 리뷰를 그대로 실행할 수 있게 하는 지시서.
> 실행 방법은 맨 아래 "실행 가이드" 참조.

## 1. 배경 / 문제 인식

vais-code (v2.2.1) 는 **비개발자 1명이 시니어 개발자처럼 개발**하는 것을 목표로 하는
Claude Code 플러그인이다. 기획 → UI/UX → 설계 → 구현 → QA 를 문서로 남기며 진행하고,
PDCA 룰을 적용한 CTO 워크플로우가 핵심이다.

**문제**: 개발 과정에서 템플릿과 참조 md 파일이 과도하게 늘어나면서
(agents 47 sub-agents + _shared 가드 + knowledge 19 MD + templates 다수),
한 phase 를 실행할 때마다 많은 파일을 읽게 되어 컨텍스트 효율이 크게 나빠졌다.

**유지해야 할 핵심 가치**: 비개발자가 지침(가드레일) 아래에서 개발하고,
중간 산출물(문서)이 남아 agent 가 세션을 넘나들며 **지속적으로 유지보수 가능한 개발**을
하는 것. 효율화를 위해 이 가치 자체를 쳐내면 안 된다.

## 2. 리뷰 성격

- **버그 찾기 리뷰가 아니다.** 설계 목표 대비 아키텍처·효율성 리뷰 + 개선 로드맵 수립이다.
- 파일별 코드 품질 지적(naming, 중복 함수)이 아니라, **"한 phase 실행 시 실제로
  무엇이 로드되는가"를 추적**해야 진짜 문제(컨텍스트 낭비)가 보인다.

## 3. 평가 기준 (제품 목표)

1. 비개발자 1명이 시니어 개발자 수준의 결과물을 내는 것
2. 중간 산출물(문서)이 남아서 agent 가 세션을 넘나들며 유지보수 가능할 것
3. 위 둘을 위한 **최소한의 지침만** 유지 — 컨텍스트 효율이 핵심 제약

## 4. 측정 항목 (추측 금지, 실제 파일 기준)

- [ ] 대표 시나리오 1개(예: `/vais cto plan → design → do`)를 따라가며
      각 단계에서 **실제 로드되는 md/js 파일 목록 + 대략적 토큰 비용** 추적
- [ ] `agents/` 47 sub-agents, `templates/`, `agents/_shared/` 가드,
      `agents/*/knowledge/` 파일 중 **실제 워크플로우에서 참조되지 않거나
      중복되는 것** 식별
- [ ] CLAUDE.md 20개 Mandatory Rules 를
      **코드(hook/script)로 강제되는 것 vs LLM 준수에만 의존하는 것**으로 분류

## 5. 산출물 스펙

- 핵심 가치(비개발자 + 문서 기반 유지보수)에 **기여하는 부분 vs 비용만 드는 부분** 구분
- 3분류 + 우선순위 로드맵 (각 항목에 예상 효과와 리스크):
  1. 지금 지우거나 합쳐도 되는 것
  2. 구조를 바꿔야 하는 것
  3. 유지할 것
- **결과는 docs 에 바로 박제하지 말고 대화로 먼저 전문 표시** → 사용자와 방향 합의 후
  이 피처 폴더에 계획 문서화

## 6. 경계 (리뷰어가 지킬 것)

- "문서를 남기는 것 자체"는 사용자의 핵심 가치다. 효율만 보고 문서 단계를 제거하는
  계획을 제안하지 말 것. 줄일 대상은 **지침/템플릿/참조 체인의 낭비**이지,
  산출물 기록 문화가 아니다.
- 리뷰(진단)와 로드맵 확정(계획)을 한 번에 끝내지 말 것. 리뷰 결과를 사용자가 보고
  "지킬 것 / 버릴 것"을 판단한 뒤 계획을 확정한다.

## 7. 실행 가이드 (다음 세션에서)

1. 이 문서를 읽는다 (`docs/260821_plugin-architecture-review/01-plan/main.md`)
2. §4 측정 항목을 수행한다 — 서브에이전트 병렬 탐색 권장.
   더 넓은 전수 조사를 원하면 사용자가 "use a workflow" 를 명시.
3. §5 스펙대로 결과를 **대화에 전문 표시**하고 사용자 판단을 받는다
4. 합의된 로드맵을 이 피처의 후속 phase 문서로 박제한다

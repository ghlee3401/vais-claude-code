# Design revision 2 — Lean Phase Transactions

## 1. 변경 이유와 목표

Design v1의 안전성과 제품 품질은 실제 `claude-opus-5` 검증에서 통과했다. 그러나 동일 Mini Booking 전체 여정 3쌍의 중앙값은 Legacy `90,757` tokens·`34,909B` Markdown 대비 v2 `362,446` tokens·`39,268B`로 효율 Gate를 실패했다. 작성 문서 수만 `6→5`로 줄었다.

이번 revision은 REQ-001의 Plan→Design→Do→Review→Report, Plan/Design 승인, 독립 QA, 최종 사용자 승인, Report 동결을 바꾸지 않는다. 긴 대화와 반복 도구 출력을 줄이는 실행 설계만 교체한다.

목표는 다음 네 가지다.

1. 다섯 Phase와 승인 Gate를 유지한다.
2. 같은 내용을 대화·문서·Agent handoff에 반복하지 않는다.
3. Design이 필요하다고 판단한 Agent만 호출하고 기계 검사는 Tool이 맡는다.
4. 통제된 실제 Opus 3회 비교에서 품질을 유지하며 token과 Markdown byte 중앙값을 Legacy보다 낮춘다.

## 2. 유지되는 불변 조건

- 사용자는 계속 `/vais` 자연어 한 창구만 사용한다.
- 활성 Work item은 하나이며 다른 요청은 새 Work item을 만들지 않고 대기한다.
- 모든 규모에서 다섯 Phase 정본은 존재한다. lean은 Phase 생략이 아니라 깊이 조절이다.
- 승인된 Plan 없이 Design, 승인된 Design 없이 Do, AI QA PASS 없이 최종 승인, 최종 승인 없이 Report는 불가능하다.
- Review FAIL은 Design을 거치지 않고 Do로 갈 수 없다.
- Independent QA는 read-only이고 구현자 자기평가를 판정 근거로 사용하지 않는다.
- write scope, lease, drift, assignment receipt, canonical Gate 재계산과 Report freeze는 완화하지 않는다.
- Ideation은 Plan에 포함하고 별도 Markdown을 만들지 않는다.

Design v1은 `revisions/v1.md`에 승인 이력으로 보존한다. 이 문서가 현재 실행 정본이며, v1을 매 Phase의 기본 컨텍스트로 다시 읽지 않는다.

## 3. 핵심 구조

```text
/vais 입력
  → State Router
  → Phase Context Capsule (현재 Phase에 필요한 최소 데이터)
  → Phase Owner 판단
  → 0~N Specialist (Design이 필요하다고 선언한 경우만)
  → 단일 Phase Transaction
  → 짧은 receipt + canonical document/evidence
  → 사용자에게 결과와 다음 승인만 표시
```

LLM은 제품 판단과 구현에 집중한다. 문서 frontmatter, Gate 검사 조합, handoff 등록, 인덱스 생성과 상태 전이는 deterministic transaction이 담당한다.

## 4. Context Capsule

### 4.1 동작

`context --phase <phase> --role <role>`은 전체 대화나 전체 선행 문서를 출력하지 않고 다음 최소 집합을 JSON으로 반환한다.

| Phase | 입력 capsule |
|---|---|
| Plan | 관련 Feature/Work item 후보, 구조화 요청 요약, 규모 후보 |
| Design | 승인 Plan의 REQ ID·판정 기준·사용자 흐름, 현재 기술 표면 |
| Do | Design 결정, TC ID, write scope, required specialist, readiness check |
| Review | REQ/TC 기대값, 실제 diff 요약, handoff/check receipt, 증거 경로 |
| Report | 승인·Gate event, 최종 변경 요약, QA verdict, 잔여 제한, 링크 |

Capsule은 원문 요구사항이나 Agent 사고 과정을 복제하지 않는다. 각 항목은 source path와 hash를 가져 stale revision을 거부한다. 실패 시 전체 파일을 자동 덤프하지 않고 필요한 경로와 finding만 반환한다.

### 4.2 크기 한도

| 규모 | Capsule 최대 출력 | transaction 표준 출력 |
|---|---:|---:|
| compact | 6KB | 1KB |
| standard | 10KB | 1KB |
| extended | 20KB | 2KB |

세부 로그와 JSON evidence는 파일에 남기고 모델에게는 요청할 때만 읽힌다. 한도 초과는 truncate가 아니라 FAIL이다. 무엇이 초과했는지 알려 capsule 선택 규칙을 수정하게 한다.

## 5. Phase Transaction

### 5.1 공통 계약

각 Phase는 여러 CLI 명령을 조립하는 대신 한 번의 transaction으로 닫는다. transaction은 현재 Work item·Phase·revision·session authorization을 다시 확인하고 아래를 원자적으로 수행한다.

1. 정본 document와 구조화 입력 검증
2. 필요한 기계 check 실행 또는 기존 runtime receipt 검증
3. required specialist의 consumed/completed handoff 확인
4. Gate 재계산
5. event 적용, snapshot·root/index 동기화
6. receipt ID, verdict, 다음 상태, finding 경로만 출력

중간 실패 시 상태 전이를 적용하지 않는다. 자세한 실패 내용은 canonical evidence에 기록한다.

### 5.2 Phase별 transaction

| Phase | transaction | 책임 |
|---|---|---|
| Plan | `plan present` | draft 저장, Plan 검사, Work item 생성/갱신, 승인 대기 |
| Design | `design present` | scope/check/specialist 저장, Design 검사, 승인 대기 |
| Do | `do ready` | handoff·Do 정본·readiness Tool 검사, Review 전이 |
| Review | `review decide` | 독립 QA handoff·review checks·정본 검사, PASS/FAIL/BLOCKED 전이 |
| Report | `report finalize` | 짧은 Report 생성/검사, Feature·Master index, completed/frozen |

Report는 이전 문서를 재서술하지 않는다. 최종 outcome, 변경 경로, QA verdict, 잔여 제한, 승인 시점과 정본 링크를 구조화 event에서 기계 생성한다. 사용자가 별도 서술을 요구할 때만 짧은 summary를 추가한다.

## 6. Agent 선택과 handoff

### 6.1 전문 영역 coverage

Design은 UI, backend/API, data, infrastructure, security/compliance, operations, business를 `필요`, `불필요`, `불확실`로 판단한다. `필요`라고 해서 항상 Agent가 필요한 것은 아니다. 아래 기준으로 사람 수준의 별도 판단이 필요한 경우에만 specialist를 선택한다.

- 다른 기술 표면과 독립된 전문 판단이 필요하다.
- 공개 계약·DB·보안·인프라처럼 main owner의 추정만으로 위험하다.
- 승인된 병렬 write scope가 실제로 분리된다.
- 새로운 테스트 전략이나 harness 설계가 필요하다.

테스트 실행, lint, audit, 정해진 Chrome 시나리오처럼 결정 규칙이 고정된 일은 Tool adapter가 맡는다. 단순히 테스트를 실행하기 위해 test-engineer를 호출하지 않는다. compact 단일 표면 구현은 Design이 근거를 남기면 CTO main owner가 직접 수행할 수 있다. Independent QA는 Review에서 항상 별도 Agent다.

### 6.2 규모별 기본 Agent 예산

| 규모 | Do specialist 기본 상한 | Review |
|---|---:|---|
| compact | 0~1 | independent-qa 1회 |
| standard | 0~2 | independent-qa 1회 |
| extended | dependency graph로 결정 | independent-qa 1회 |

상한을 넘길 때는 Design에 추가 역할, 독립 질문, 비중복 write scope를 명시한다. 문서 작성만을 위한 Agent와 동일 역할 중복 호출은 금지한다.

### 6.3 자동 handoff 박제

Agent prompt에는 기존처럼 AS receipt 하나만 보낸다. PostToolUse가 Agent의 specialist-handoff/v1을 schema·digest·Design revision과 대조해 evidence에 직접 저장하고 assignment를 완료 처리한다. main Agent가 JSON을 다시 Write하고 `handoff` CLI를 호출하는 두 단계를 제거한다. 불완전·stale·복수 receipt는 fail closed한다.

## 7. Markdown 예산과 중복 금지

### 7.1 규모별 기본 byte 예산

| Phase | compact | standard | extended |
|---|---:|---:|---:|
| Plan | 5.5KB | 6.0KB | 10KB |
| Design | 8.0KB | 10KB | 18KB |
| Do | 2.5KB | 3.5KB | 6KB |
| Review | 5.0KB | 6.0KB | 10KB |
| Report | 2.5KB | 3.0KB | 5KB |

compact/standard 초과는 document-budget check가 Gate를 차단한다. 내용상 한도가 부족하면 규모를 올려 사용자에게 보여준다. extended 초과는 Design에 `budget_exception` 이유와 사용자 승인이 있어야 한다. 기계 evidence, 로그, 이미지와 생성 index는 이 authored Markdown 예산에 포함하지 않되 별도 크기를 관찰한다.

### 7.2 Phase별 단일 책임

- Plan만 문제·목표·범위·REQ 설명·사용자 흐름·엣지 케이스·완료 조건을 소유한다.
- Design은 REQ ID별 동작, 입력, 출력, 오류, 기술 결정, TC, scope만 기록한다. Plan 문장을 복사하지 않는다.
- Do는 변경 파일, handoff receipt, readiness 결과와 Design 차이만 기록한다.
- Review는 REQ/TC별 `입력·기대·실제 출력·판정·evidence` 한 행과 제한만 기록한다.
- Report는 최종 결과·승인·변경·검증·제한·링크만 기록한다. 앞 문서의 표를 복제하지 않는다.

긴 동일 문장이 여러 Phase에 반복되면 repetition check가 finding을 낸다. ID와 링크의 반복은 허용한다.

## 10. Do dispatch 설계

이번 변경은 runtime·hook·evaluation이 함께 바뀌는 extended 작업이다.

| Wave | 담당 Agent | 질문 | write scope |
|---|---|---|---|
| 1 | backend-engineer | capsule, phase transaction, document budget, auto handoff를 기존 불변 조건과 결합 | `lib/workflow/v2/**`, `hooks/workflow-v2-*.js`, `scripts/vais-workflow-v2.js`, `schemas/**` |
| 2 | test-engineer | transaction·budget·handoff 공격 사례와 clean live evaluator 구축 | `tests/v2-*.test.js`, `tests/fixtures/**`, `scripts/evaluation/**` |

두 Wave는 production/test write scope가 분리되므로 병렬 가능하되, Wave 2는 Wave 1의 공개 함수 계약만 사용한다. main CTO는 `skills/vais/SKILL.md`, `vais.config.json`의 shadow 유지, 통합 문서만 담당한다. frontend·UI·인프라·운영·business Agent는 불필요하다.

## 11. Readiness와 Review Gate

### Readiness

- 전체 unit/integration test 0 FAIL
- lint 0 warning
- plugin validator PASS
- live-shadow evidence schema PASS
- capsule/transaction/document-budget/auto-handoff 공격 테스트 PASS
- source mode `shadow`

### Review

- Independent QA read-only clean-room 1회
- 실제 Chrome과 canonical artifact 검사
- 동일 immutable stage, 동일 Opus·effort·격리 tool profile의 Legacy/v2 전체 여정 각 3회
- 양쪽 terminal completed·quality PASS
- v2 required Agent 100% 완료, duplicate 0
- v2 median total cache-creation tokens < Legacy
- v2 median authored Markdown count와 bytes < Legacy

Formal 성능 run에는 quota 복구, 라우터 공격, 조건부 승인 시험을 섞지 않는다. 그것들은 별도 robustness corpus로 실행한다. provider total token은 실제 비용 관찰값으로 유지하고, capsule bytes·tool result bytes·document bytes를 원인 지표로 함께 기록한다.

## 12. Rollback과 Gate

- 구현과 검증 동안 `workflowV2.mode`는 `shadow`를 유지한다.
- transaction 또는 handoff가 불안정하면 기존 세분화 CLI 경로로 되돌릴 수 있도록 제거하지 않고 compatibility layer로 둔다.
- 실제 Shadow 효율이 다시 실패하면 자동 Repair를 시작하지 않고 Review FAIL로 사용자에게 돌아온다.
- PASS와 사용자 최종 승인 전에는 source Report·기본 엔진 전환·배포를 하지 않는다.

### Design Gate 상태

- Plan 목표와 공개 사용자 흐름 변경: 없음
- 기술 실행 방식의 실질 변경: 있음 — Design revision 2 및 사용자 승인 필요
- 구현 준비 상태: 사용자 승인 완료
- 다음 단계: Do Wave 1·2 → Readiness → Review

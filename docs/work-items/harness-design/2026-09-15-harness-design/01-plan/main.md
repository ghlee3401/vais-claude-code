# Plan — 하네스 설계 문서 (harness-design)

## 한 줄 요약 (비개발자용)

비개발자가 개발자처럼 웹 앱을 만들 수 있게, 요구사항부터 구현까지 11단계 사슬을 단계마다 문서·승인·ID·기록으로 묶고 runtime 이 뭉개기를 막는 하네스의 **설계 문서**를 만든다. 이 작업은 코드를 바꾸지 않는다.

## 1. 문제

- 개발 사슬(요구사항 → 기능 → 화면 → 와이어 → 디자인 → 시안 → 데이터 → API → 기술 구조 → 테스트 → 구현)이 지금 커널에는 Plan/Design 두 문서로 뭉개져 있어, 결정이 문서에 남지 않고 다음 세션의 AI 가 빈 자리를 임의로 채운다.
- 전체 기능 정의서가 없어 "지금 무엇이 구현됐는지" 를 볼 수 없다.
- UI 수정 결과를 그림으로 승인·확인하는 길이 없어 원하는 화면이 나오지 않는다.
- 결정·피드백·부채가 어디에도 누적되지 않아 연속성이 끊긴다.
- 역할(기획자·디자이너·개발자·QA)이 예전에는 85개 프롬프트 파일로 흩어져 컨텍스트를 낭비했고, 지금은 카드만 남아 단계와 연결되지 않았다.
- 커널 결함: mode 대소문자 오류 시 무음 비활성, 한글 요청의 해시 slug, lease 60초 하드코딩, 읽기 명령·scratchpad 차단, router 의 평가용 문장, `commit`/`help` 부재, Plan 수정 시 지시된 초안 경로가 쓰기 범위 밖.

## 2. 목표

빠지는 단계 없는 하네스 설계 정본을 작성해 사용자 승인을 받고, 이후 구현 작업(후속 Work item)의 유일한 기준으로 삼는다.

## 3. 범위

포함: 설계 문서 1부 (`docs/` 첫 문서), 후속 Work item 로드맵.
제외: 코드·hook·CLI 변경, 플러그인 배포·버전 bump, 실제 제품 앱 개발.

## 4. 요구사항

| ID | 요구사항 | 완료 조건 |
|---|---|---|
| REQ-001 | 문서 맨 위에 비개발자용 한 장 요약을 둔다. | 300자 이내 요약만 읽고 승인 판단이 가능하다. |
| REQ-002 | 개발 사슬 11단계 각각을 별도 문서로 정의한다. | 단계마다 ID 접두, 필수 항목, 고르기·확인 산출물, 승인 문구가 표로 있다. |
| REQ-003 | ID 사슬 규칙을 정의한다. | 부모 ID 없는 항목 저장 거부, 상위 변경 시 하위 stale 표시, 구현 Design 은 ID 인용만 허용. |
| REQ-004 | 단계별 억지력을 손잡이 5개(Prompt·PreToolUse·PostToolUse·Stop·CLI)와 상태 줄에 대응시킨다. | 11단계 × 억지력 5종 표에 빈칸이 없다. |
| REQ-005 | 루프 하나와 일 양식(기능·UI·버그)이 사슬 문서를 어떻게 읽고 갱신하는지 정의한다. | 양식마다 읽는 문서·건드리는 ID·갱신 문서가 명시된다. |
| REQ-006 | 제품 노트(현재·다음·왜·과거)와 세션 브리핑, 상태 줄을 정의한다. | 노트 4면의 출처 파일과 갱신 시점이 명시된다. |
| REQ-007 | 명령 다섯(상태·설명·저장·되돌리기·doctor)을 정의한다. | 각 명령의 입력·출력·읽기/쓰기 여부가 표로 있다. |
| REQ-008 | 바탕 셋(기억·안전·확장)의 구체 규칙을 정의한다. | 자동 기록 지점, 비상 해제 스위치, 버전 도장, 회귀 세트가 명시된다. |
| REQ-009 | 설계 요소 → 담당 파일 대응표를 만든다. | 대응표에 빈칸이 0이다. |
| REQ-010 | 사용 장면 6개(시작·기능·UI 3회·버그·재개·고장)를 문서로 걸어본다. | 각 장면이 막힘 없이 끝까지 서술된다. |
| REQ-011 | 현 커널 결함과 처리 방안을 목록화한다. | 1절 결함 전부에 해결 작업 번호가 붙는다. |
| REQ-012 | 후속 Work item 로드맵을 정의한다. | 작업마다 규모·순서·완료 조건·의존이 있다. |
| REQ-013 | 단계별 역할(기획자·UI 디자이너·개발자·QA 등)을 역할 카드로 정의하고, 카드에서 만든 전용 프롬프트를 단일 실행 Agent 가 받아 일한다. 사용자는 역할을 고르지 않는다. | 11단계마다 owner 역할과 허용 specialist 가 표로 있고, 역할 산출물은 handoff 요약이 아니라 해당 단계 문서에 직접 쓰인다. |
| REQ-014 | 별도 Agent 를 띄우는 기준을 정의한다. | 독립성 필요(QA)·문맥 격리 이득(화면 설계)·병렬 가능(규약 확정 후 프론트/백) 세 조건 중 하나 이상일 때만 띄우고, 그 외는 본 목소리가 직접 수행한다. |

## 5. 사용자 흐름

1. 사용자가 이 Plan 을 승인한다.
2. VAIS 가 Design 단계에서 설계 문서 본문을 쓰고 한 장 요약과 함께 제시한다. 사용자는 요약을 읽고 승인하거나 수정을 말한다.
3. Design 승인 후 VAIS 가 문서를 `docs/` 정본 위치에 확정하고, 독립 검토가 REQ-001~014 충족을 확인한다.
4. 사용자가 최종 승인하면 Report 로 동결하고, 로드맵 첫 작업을 제안한다.

## 6. 엣지 케이스

| 상황 | 처리 |
|---|---|
| 설계 문서가 extended 예산(18,432B)을 넘음 | 사유를 적고 사용자 승인으로 예산 예외를 받는다. |
| 설계 중 새 단계나 결함이 발견됨 | Design revision 으로 추가하고 사용자에게 다시 보인다. |
| 새 설계가 현 커널 규칙과 충돌함 | 충돌 목록을 문서에 남기고 후속 작업으로 배정한다. 이 작업에서 커널을 고치지 않는다. |
| 사용자가 특정 단계를 빼자고 함 | 뺀 이유를 결정으로 기록하고 사슬 표를 갱신한다. |
| 역할 Agent 의 산출물이 handoff 한도(3KB)를 넘음 | 산출물은 단계 문서에 직접 쓰고 handoff 에는 receipt 와 판정만 남긴다. |

## 7. 완료 조건

- 설계 문서가 `docs/` 에 존재하고 REQ-001~014 를 모두 충족한다.
- 대응표 빈칸 0, 사용 장면 6개 통과.
- 사용자 최종 승인.

## 8. 영향

- 코드·hook·설정 변경 없음. `docs/` 에 첫 문서가 생긴다.
- 이후 모든 구현 작업은 이 문서의 ID 와 로드맵을 인용해야 한다.
